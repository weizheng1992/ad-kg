# T5 案例生成生命周期场景（4~6 个）

## Question

案例生成是多步流：`/agent/chat` 产出 case_draft → materialize 服务端对齐/建号 → 前端确认 → `/ingest/case-commit` 服务端重校验落图。golden 一问一答装不下，走**独立场景脚本通道**（T1 执行器的场景断言能力），出 **4~6 个端到端场景**：

> **T1 实弹已知事实（2026-10-29）**：① case_seed 生成有 LLM 抖动（同场景一轮直 final 无 seed、一轮先搜知识后正确产出）——场景失败先重跑再改措辞，判据别把抖动当缺陷；② ae 行权限下 agent 看不见 scope 外品牌但服务端对齐仍正确命中（两层各司其职）——可加诚实性断言场景；③ create_case 动作门只有 ae/admin（§12.4）。详见 T1 Answer。

- ** happy path**（2~3 个）：真实口吻任务（"把上个月小红书那个爆量视频案例录进来，投放时间 6 月到 8 月，预算 80 万"）→ 断言 draft 事件字段齐（实体、时间窗、指标、来源引用）→ commit → 图上落点断言（`{class}:{slug}` 建号、对齐 L1 过、authority 四元组对、platform ID 只进 entity_alias）
- **对齐路场景**（1~2 个）：草稿实体带平台侧 ID/别名 → 断言只作 external_id 进 alias 不污染主实体（实测教训的回归面）
- **仲裁/拦截场景**（1 个）：抽取产物遇更高权威在场 → 断言不覆盖、进人审队列（§12.2 四路统一仲裁的回归面）
- **失败诚实场景**（1 个）：信息不全的口吻任务（"帮我把那个案例记一下"没说哪个）→ 断言 agent 反问/拒绝而不瞎编草稿
- **判据**：场景断言全过计（不走 judge 百分比）；断言里守铁律——未对齐产物不得直接入图
- **清理**：场景跑完回滚测试写入（幂等清理或用标记实体隔离），不留脏数据

## 验收

- 4~6 场景脚本化、可一条命令重跑；两轮全过
- 图上无场景残留脏数据（清理断言）
- 报告落 `eval/runs/`；文档同批改
